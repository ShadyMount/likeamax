# Telegram через GREEN-API

Минимальный React-клиент: подключение, загрузка существующих личных чатов, история переписки, создание чата по телефону, отправка и получение текстовых сообщений. Интерфейс на русском в стиле Telegram Web.

В списке есть поиск по имени и известному номеру телефона, время последнего сообщения и статусы исходящих. Кнопка «Новый чат» открывает форму номера. В переписке сообщения сгруппированы по дням, короткая история расположена у поля ввода. На телефоне список и переписка занимают отдельные экраны; кнопка «Назад к чатам» возвращает к списку, черновики сохраняются до выхода.

## Запуск

Нужен Node.js 24.x: эта версия совместима с ESLint и Steiger.

```sh
npm install
npm run dev
```

Открыть адрес из терминала (обычно http://127.0.0.1:5173).

```sh
npm run build
npm run preview
```

## Подготовка GREEN-API

1. Создать **Telegram-инстанс** в https://console.green-api.com/ и авторизовать свой Telegram-аккаунт.
2. В настройках инстанса очистить `webhookUrl`, включить `incomingWebhook` (получение входящих сообщений). После изменения подождать около минуты.
   Для синхронизации сообщений, отправленных с телефона, включить `outgoingMessageWebhook`; для сообщений через API — `outgoingAPIMessageWebhook`; для статусов доставки и прочтения — `outgoingWebhook`. Без этих дополнительных уведомлений история загружается при открытии диалога, но изменения исходящих сообщений в реальном времени могут не приходить. Приложение само не изменяет настройки инстанса.
3. Скопировать `idInstance`, `apiTokenInstance` в форму подключения. API URL по умолчанию — `https://4100.api.green-api.com`; если в кабинете указан другой адрес, заменить его.
4. Выбрать существующий чат либо ввести международный номер получателя, открыть чат, отправить текст. Ответить с аккаунта получателя в Telegram — ответ появится автоматически.

## Границы минимальной версии

- Только текст, личные диалоги с людьми и ботами, до 4096 символов. Enter отправляет, Shift+Enter переносит строку. Входящие сообщения ботов обновляют открытую переписку и предпросмотр в списке без повторного открытия чата.
- Для поиска номера используется `CheckAccount`. Если номер скрыт настройками приватности Telegram, чат по нему открыть не получится.
- При входе запрашивается список личных чатов через `GetChats`, затем последние 100 сообщений каждого чата через `GetChatHistory` для предпросмотра последнего текста. Если имя в списке отсутствует, оно загружается через `GetContactInfo`: имя из контактов, имя профиля, затем username. Технический ID в заголовке не показывается. Строки списка заполняются постепенно, с учётом ограничения истории в один запрос в секунду.
- При открытии диалога история обновляется; совпадающие запросы объединяются, сообщения не дублируются. Отображаются только текстовые сообщения в хронологическом порядке. Подгрузки более старой истории нет. Ошибки загрузки можно повторить кнопкой. Пустой диалог обозначается «Нет текстовых сообщений», ошибка загрузки отличается от пустого диалога.
- `SendMessage` подтверждает постановку в очередь. Подпись «В очереди» не подтверждает доставку. Доставка, прочтение и ошибки отправки отображаются по данным истории и уведомлений GREEN-API; без соответствующих уведомлений статус не обновится до повторного открытия диалога.
- Поддерживаются обычный текст, текст со ссылкой, эмоджи и переносы строк. Исходящие сообщения из телефона и API синхронизируются при включённых уведомлениях, повторные события не создают дубли.
- Переписка сортируется по серверному времени сообщения; при совпадении секунды числовые `idMessage` сравниваются без потери точности. Время из браузера используется временно до получения серверных данных и не перезаписывает их. Чаты упорядочены по последнему сообщению, запоздавшие уведомления не заменяют более новый предпросмотр.
- Получение: последовательные `ReceiveNotification` и `DeleteNotification`, повтор после сбоя через 5 секунд, исключение дублей по ID сообщения внутри чата.
- История, черновики и реквизиты находятся только в памяти вкладки. После перезагрузки потребуется снова войти; чаты и последние сообщения будут повторно загружены из GREEN-API. Обработанные уведомления удаляются из очереди GREEN-API.
- Прямые HTTPS-запросы из браузера к GREEN-API; сервер и база данных не требуются. Токен доступен в памяти браузера и его сетевых запросах.

## Технологии

React 19.3.1, TypeScript 6.0.3, Vite 8.3.5. Точные зависимости закреплены в `package-lock.json`. TypeScript 6 выбран из-за поддержки в `typescript-eslint`: версия 7 пока не входит в поддерживаемый диапазон. Для состояния используются хуки React, для API — встроенный `fetch`, для оформления — CSS Modules.

Иконки — Ionicons из `react-icons`.

## Структура кода

Модульная архитектура с направлением зависимостей FSD: `app → pages → widgets → features → entities → shared`.

```text
src/
  app/                       # Корневой компонент, сессия, сброс и CSS-переменные
  pages/messenger/           # Сборка экрана из виджетов и действий
  widgets/chat-sidebar/      # Список, поиск, открытие формы нового чата
  widgets/conversation/      # Шапка, даты, история и прокрутка
  features/connect-instance/ # Форма подключения к GREEN-API
  features/messaging/        # Состояние, загрузка, polling, отправка, черновики
  entities/chat/             # Типы, сортировка, дедупликация и отображение сообщений
  shared/api/                # HTTP-клиент GREEN-API, отмена и ограничение частоты
  shared/lib/                # Форматирование дат
  shared/ui/                 # Общий аватар и стили UI-примитивов
  main.tsx                   # Только монтирование приложения
```

`useMessenger` связывает сценарии и хранит выбранный чат; виджеты получают данные и обработчики через props. Внутри `features/messaging/model` обязанности разделены:

- `chatReducer` — обновление чатов, сообщений и кэша статусов без сетевых запросов.
- `useChatDirectory` — список чатов, имена контактов и постепенная загрузка превью.
- `useChatHistory` — история выбранного чата, повтор загрузки и объединение параллельных запросов.
- `useMessageNotifications` — последовательное получение и подтверждение уведомлений, повтор после ошибок.
- `messageMappers` — преобразование истории и уведомлений GREEN-API в сообщения и события приложения; медиа и неподдерживаемые события отфильтровываются здесь.
- `useMessageComposer` — черновики по чатам и отправка сообщений.
- `useCreateChat` — проверка номера и открытие диалога.

На странице состояния сгруппированы по сценарию: `messenger.list`, `messenger.history`, `messenger.creation` и `messenger.composer`. Внутренние хуки и reducer не экспортируются из публичного API слайса. Подключение владеет созданием API-клиента, `App` — временем жизни сессии. Транспортные типы описывают ответы GREEN-API, типы `Chat` и `Message` — состояние интерфейса. В `shared/api/types.ts` контракт `ApiMethods` связывает имя метода, аргументы и ответ: например, `api.request('sendMessage', { chatId, message })` возвращает `{ idMessage: string }`. Для нового метода сначала добавляется контракт; указываются только используемые приложением поля. Эти типы проверяют вызовы при разработке, но не валидируют JSON-ответ сервера во время выполнения.

Стили компонентов находятся рядом с ними в `*.module.css` и импортируются через объект `styles`. Глобально подключаются только `app/styles/tokens.css` и `app/styles/base.css`: тема, сброс, фокус и базовые состояния HTML. Общие классы кнопок, полей, подписей и ошибок вынесены в `shared/ui/primitives.module.css`. Виджеты принимают `className` для компоновки страницы; цвета статусов передаются через CSS-переменные. Селекторы не обращаются к внутренним классам соседних модулей. Тесты используют роли, подписи и стабильные атрибуты вместо генерируемых CSS-классов.

У слайсов и сегментов Shared есть публичные API в `index.ts`. Внешний код импортирует их через корень, внутренние импорты слайса остаются относительными. UI виджетов находится в сегменте `ui`.

## Руководство для разработчика

### С чего начать чтение

1. [App.tsx](src/app/App.tsx) — переключение между подключением и чатом, завершение сессии.
2. [MessengerPage.tsx](src/pages/messenger/ui/MessengerPage.tsx) — соединение данных и обработчиков с интерфейсом.
3. [useMessenger.ts](src/features/messaging/model/useMessenger.ts) — сборка сценариев; затем нужный хук из списка выше.
4. [chatReducer.ts](src/features/messaging/model/chatReducer.ts) и [messages.ts](src/entities/chat/model/messages.ts) — обновление состояния и правила сообщений.

### Как проходят данные

- **Подключение:** `ConnectForm → useConnectInstance → createApi`. Хук проверяет авторизацию и настройки уведомлений, затем передаёт клиент в `App`. При выходе клиент отменяет запросы, экран чата размонтируется и его состояние удаляется.
- **История:** `useChatDirectory / выбор чата → useChatHistory → getChatHistory → mapHistoryMessages → history-loaded → chatReducer`. Преобразователь отбирает текст, reducer объединяет его с уже полученными сообщениями и статусами.
- **Входящее событие:** `useMessageNotifications → receiveNotification → mapNotification → dispatch / ошибка доставки → deleteNotification`. Даже неподдерживаемое событие подтверждается, чтобы очередь продолжала работать. Если подтверждение не удалось, событие может прийти повторно.
- **Отправка:** `Composer → useMessageComposer → sendMessage → message-added`. После ответа появляется сообщение со статусом очереди и временной отметкой браузера. Уведомление или история уточняют время и статус; фоновая загрузка истории не отменяет успешную отправку.
- **Отображение:** `chatReducer → useMessenger → MessengerPage → виджеты`. `MessageList` отвечает за текст, разделители дат и прокрутку; сетевых запросов в нём нет.

### Где делать изменения

| Задача                                | Место изменения                                                                                          | Что проверить                                                                          |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Новый используемый метод GREEN-API    | `shared/api/types.ts`: добавить аргументы и ответ в `ApiMethods`; вызвать метод из соответствующего хука | `tests/types/api.test.ts`, затем мок нужного ответа API                                |
| Новый формат текста или уведомления   | `features/messaging/model/messageMappers.ts`                                                             | `tests/unit/message-mappers.test.mjs` и браузерный сценарий `notifications` или `bots` |
| Сортировка, дубли, приоритет статусов | `entities/chat/model/messages.ts`; для переходов состояния — `chatReducer.ts`                            | `tests/unit/messages.test.mjs`, `chat-reducer.test.mjs`, сценарий `message-order`      |
| Новое действие пользователя           | Компонент и хук соответствующей feature; если меняются чаты — тип действия и обработка в reducer         | Изолированный сценарий в `tests/scenarios/`; чистые правила отдельно в `tests/unit/`   |
| Изменение внешнего вида               | Компонент и его CSS Module; раскладка экрана — `MessengerPage.module.css`                                | Нужный браузерный сценарий, включая `mobile` для адаптивной раскладки                  |

Новую feature стоит выделять под самостоятельное действие пользователя. Функции преобразования и вспомогательные хуки остаются внутри существующего слайса, пока относятся к тому же сценарию. Экспорт в `index.ts` добавляется только для использования снаружи слайса.

### Правила, которые важно сохранить

- ID сообщений и чатов остаются строками. Числовые ID сообщений могут превышать безопасный диапазон `number`.
- Сортировка и объединение сообщений выполняются общими функциями из `entities/chat`. Серверное время заменяет временную отметку браузера; повторное событие не создаёт второе сообщение, запоздалый статус не отменяет прочтение.
- Reducer не выполняет запросы и не изменяет предыдущий снимок состояния. Преобразователи не читают состояние React: они только переводят данные API в модель приложения.
- Очередь опрашивается последовательно. Изменение черновика или выбранного чата не должно перезапускать эффект опроса и отменять общий API-клиент.
- Поздний ответ истории объединяется с актуальным состоянием чата. После переключения он не должен менять индикатор загрузки другого диалога.

Перед завершением изменения запустите `npm run check`. Если меняется поведение, сначала добавьте проверку, которая воспроизводит нужный случай. Для браузерного теста подготовьте собственное состояние через `tests/helpers/session.mjs`, включите необходимые ошибки в его моке и зарегистрируйте сценарий в `tests/smoke.mjs`; не вызывайте другой тест ради подготовки.

## Проверка

```sh
npm run lint          # ESLint: JavaScript/TypeScript и React Hooks; Steiger: архитектура
npm run format:check  # Проверка форматирования без изменения файлов
npm run format       # Применение Prettier
npm run test:types   # Проверка контрактов API компилятором TypeScript
npm run test:unit    # Правила сообщений, reducer и преобразование данных без браузера
npm run test:browser # Все браузерные сценарии
npm run check        # Линтеры, форматирование, все тесты и сборка
```

Для отдельного запуска передайте идентификатор сценария; несколько идентификаторов выполняются в указанном порядке:

```sh
npm run test:browser -- notifications
npm run test:browser -- mobile search
```

Доступные сценарии: `connection`, `sending`, `notifications`, `drafts`, `message-order`, `bots`, `search`, `mobile`.

Модульные тесты в `tests/unit/` проверяют порядок и дедупликацию сообщений, серверное время, приоритет статусов, гонки истории с уведомлениями и преобразование ответов API. Они запускаются встроенным `node:test`; для загрузки reducer с импортами проекта используется Vite без HTTP-сервера.

Браузерные проверки запускаются через `tests/smoke.mjs`: он поднимает Vite и выполняет именованные сценарии из `tests/scenarios/`. Мок GREEN-API и очередь уведомлений находятся в `tests/helpers/green-api-mock.mjs`. У каждого сценария отдельный браузерный контекст и мок API, поэтому состояние не зависит от предыдущих проверок. Подготовка подключения и чата выполняется через интерфейс в `tests/helpers/session.mjs`; ошибки API включаются явно в нужном сценарии. Ответы API подменяются, реальные реквизиты не нужны. Ошибка одного сценария не мешает выполнить остальные, но весь запуск завершается с ненулевым кодом.

ESLint использует flat config, рекомендуемые правила JavaScript/TypeScript и две проверки React Hooks: порядок вызовов и зависимости эффектов. Для `src` включён анализ типов через `projectService` и правило `@typescript-eslint/no-deprecated`, которое обнаруживает устаревшие типы и API. `eslint-config-prettier` отключает конфликты с форматтером; Prettier запускается отдельно.

Steiger использует рекомендуемый набор FSD. Проверки импортов между слоями, публичных API и структуры включены. Отключена только рекомендация `insignificant-slice`: в одностраничном приложении `features/messaging` и два крупных виджета намеренно имеют одного потребителя. Число использований не определяет необходимость отдельного модуля. Исключение описано в `steiger.config.js`.

У текущего Steiger есть транзитивная dev-зависимость `braces`, для которой `npm audit` сообщает об уязвимости обработки вложенных glob-шаблонов; исправленная версия пока не доступна. Линтер получает только локальные шаблоны из конфигурации. `npm audit --omit=dev` не находит уязвимостей в production-зависимостях. Принудительные несовместимые обновления не применялись.

Перед первым запуском браузерных тестов установите Chromium:

```sh
npx playwright install chromium
npm test
```

Браузерный запуск поднимает Vite на порту 5174 и выполняет сценарии с имитацией GREEN-API: загрузку существующих чатов и истории, повтор после ошибок, порядок и фильтрацию текстов, недоступный номер, отправку и получение ответов, ссылки, сообщения с телефона, отсутствие дублей, обновление статусов, черновики, Unicode, переносы строк, лимит 4096 символов, мобильную ширину и остановку запросов при выходе. Реальные реквизиты не используются, запросы к GREEN-API перехватываются. Для уже установленного Chromium можно указать путь переменной `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`.

## Автоматические проверки на GitHub

Workflow [ci.yml](.github/workflows/ci.yml) запускает `npm run check` при push и в pull request. Используется Ubuntu 24.04, Node.js 24.x, установка зависимостей через `npm ci` и Chromium с системными библиотеками. Кэш npm привязан к lock-файлу; реальные реквизиты GREEN-API и секреты для проверок не нужны.

Настройка Node.js и кэша следует [документации setup-node](https://github.com/actions/setup-node); установка браузера — [рекомендациям Playwright для CI](https://playwright.dev/docs/ci). Результаты доступны во вкладке Actions и в проверках pull request. Workflow проверяет проект, но не публикует приложение на Vercel.

Для запуска workflow загрузите проект вместе с `.github/workflows/ci.yml` и `package-lock.json` в GitHub-репозиторий с включёнными Actions. Чтобы успешная проверка была обязательна перед слиянием, после первого запуска добавьте её как required status check в правилах целевой ветки репозитория. Сам файл workflow не запрещает слияние при ошибке.
